EVALRIGHT - UPDATED ORDER STORAGE PROCESS IN POSTGRESQL DATABASE

This document updates the original EvalRight order storage process for
storing candidate BGV orders when a client places an order from the
Client Portal.

================================================================================ 1.
COMPLETE DATA FLOW
================================================================================

STEP 1: CLIENT PLACES ORDER The client selects candidate details,
branch, package (optional), BGV services, priority, documents, and
consent information.

STEP 2: API POST REQUEST Endpoint: POST /api/orders

Headers: Content-Type: application/json Authorization: Bearer
Idempotency-Key:

Body: - applicant details - branch_id - package_id (optional) - selected
service IDs - priority (optional) - consent reference where applicable

IMPORTANT: Do not trust company_id from the frontend. Derive company_id
from the authenticated client user.

STEP 3: AUTHENTICATE CLIENT USER Verify: - Access token/session - User
exists - User is active - User belongs to a valid client company

STEP 4: AUTHORIZE ORDER CREATION Allowed roles may include: -
CLIENT_ADMIN - CLIENT_USER

Recommended permission: - order:create

Verify branch access through user_branches.

STEP 5: VALIDATE REQUEST Validate: - Applicant fields - Email and phone
format - DOB - branch_id - package_id - service IDs - priority -
documents - consent requirements

STEP 6: IDEMPOTENCY CHECK Use: orders.idempotency_key VARCHAR UNIQUE

Logic: - New key -> continue - Existing valid retry -> return existing
order - Invalid reuse -> reject

This prevents duplicate orders from double-clicks or network retries.

STEP 7: VALIDATE BRANCH, PACKAGE, AND SERVICES Verify: - Branch belongs
to authenticated company - User can access branch - Package is active
and available - Services are active - Package services are valid -
Provider mappings exist where required

STEP 8: LOAD AUTHORITATIVE PRICES Never trust frontend prices.

Recommended pricing priority: 1. company_service_pricing 2. negotiated
package/service price 3. services.base_price fallback

Calculate: - subtotal - discount_amount - tax_amount - total_amount -
currency

Snapshot charged prices for historical billing.

STEP 9: BEGIN DATABASE TRANSACTION BEGIN;

STEP 10: FIND OR CREATE APPLICANT Do not always insert a new applicant.

Logic: - Search within authenticated company only - If applicant exists
-> reuse applicant_id - Otherwise -> create applicant

Do not deduplicate globally across companies.

Recommended applicants fields: - id UUID PK - company_id UUID FK -
created_by UUID FK - first_name - middle_name NULL - last_name - email -
phone - dob - status - created_at - updated_at

STEP 11: STORE APPLICANT ADDRESS / CONTACT Use applicant_addresses: -
id - applicant_id - address_type - street1 - street2 - city - state -
country - zip_code - is_current - created_at

Optional contacts may use applicant_contacts.

STEP 12: STORE IDENTITY DOCUMENTS SAFELY Do not use ssn_encrypted to
store Aadhaar.

Recommended table: identity_documents - id UUID PK - applicant_id UUID
FK - document_type - document_number_encrypted - document_number_hash -
last_four NULL - country_code - created_at - updated_at

Examples: - AADHAAR - PAN - PASSPORT - DRIVING_LICENSE - SSN

STEP 13: CREATE MAIN ORDER Table: orders

Recommended fields: - id UUID PK - company_id UUID FK - branch_id UUID
FK - applicant_id UUID FK - package_id UUID FK NULL - ordered_by UUID
FK - order_number VARCHAR UNIQUE - idempotency_key VARCHAR UNIQUE -
status VARCHAR - priority VARCHAR - currency VARCHAR - subtotal
NUMERIC(12,2) - discount_amount NUMERIC(12,2) - tax_amount
NUMERIC(12,2) - total_amount NUMERIC(12,2) - notes TEXT NULL -
submitted_at TIMESTAMPTZ NULL - expected_completion_at TIMESTAMPTZ
NULL - completed_at TIMESTAMPTZ NULL - created_at TIMESTAMPTZ -
updated_at TIMESTAMPTZ

Initial status may be: - DRAFT - PENDING_CONSENT - READY_FOR_SUBMISSION

STEP 14: GENERATE SAFE ORDER NUMBER Examples: EVR-2026-000001
EVR-2026-000002

Do not use SELECT COUNT(*) + 1. Use a PostgreSQL sequence or another
concurrency-safe mechanism.

STEP 15: CREATE ORDER VERIFICATIONS For each selected service insert one
row into order_verifications.

Recommended fields: - id UUID PK - order_id UUID FK - service_id UUID
FK - provider_id UUID FK NULL - verification_type_id UUID FK NULL -
status VARCHAR - unit_price NUMERIC(12,2) - discount_amount
NUMERIC(12,2) - tax_amount NUMERIC(12,2) - final_price NUMERIC(12,2) -
provider_case_id VARCHAR NULL - findings JSONB NULL - remarks TEXT
NULL - started_at TIMESTAMPTZ NULL - completed_at TIMESTAMPTZ NULL -
created_at TIMESTAMPTZ - updated_at TIMESTAMPTZ

STEP 16: SNAPSHOT SERVICE PRICES services.base_price = current catalog
price order_verifications.unit_price = historical charged price

Also snapshot: - discount_amount - tax_amount - final_price

Never recalculate old orders only from current service prices.

STEP 17: LINK OR STORE CONSENT Table: consents - id UUID PK -
applicant_id UUID FK - order_id UUID FK - consent_type -
consent_version - ip_address - signed_at - document_url NULL -
created_at

Status logic: - Missing required consent -> PENDING_CONSENT - Consent
present -> READY_FOR_SUBMISSION

STEP 18: CREATE ORDER STATUS HISTORY Table: order_status_history - id
UUID PK - order_id UUID FK - old_status NULL - new_status - changed_by
UUID FK - changed_at - reason NULL

STEP 19: CREATE ACTIVITY LOG Table: activity_logs - id UUID PK - user_id
UUID FK - company_id UUID FK - action = create_order - module = orders -
record_id - old_values JSONB NULL - new_values JSONB NULL - ip_address -
user_agent - created_at

Never log raw Aadhaar, SSN, passwords, tokens, or API keys.

STEP 20: COMMIT If all local writes succeed: COMMIT;

If any fail: ROLLBACK;

================================================================================
2. THIRD-PARTY BGV API FLOW - AFTER COMMIT
================================================================================

IMPORTANT: Do not call the third-party BGV API inside the main SQL
transaction.

Correct flow: Store local order -> COMMIT -> Queue provider submission
-> Call third-party API

STEP 21: QUEUE PROVIDER SUBMISSION After COMMIT: - Create background
job - Include order_id or verification_id - Worker processes provider
submission

Recommended: - Outbox table + worker, or - Durable job queue

STEP 22: CREATE BGV API REQUEST RECORD Table: bgv_api_requests - id UUID
PK - order_id UUID FK - order_verification_id UUID FK NULL - provider_id
UUID FK - endpoint - request_payload JSONB - response_payload JSONB
NULL - provider_reference_id NULL - status - attempt_number INT -
requested_at - completed_at NULL - created_at

Redact/encrypt sensitive payload fields.

STEP 23: CALL THIRD-PARTY PROVIDER Worker: 1. Builds provider payload 2.
Calls provider API 3. Stores response 4. Stores provider reference/case
ID 5. Updates request status 6. Updates verification status

Typical flow: READY_FOR_SUBMISSION -> SUBMITTED -> IN_PROGRESS

STEP 24: HANDLE PROVIDER FAILURE On failure: - Record safe error
details - Increment attempt number - Retry according to policy - Avoid
duplicate provider cases - Use provider idempotency where supported

Possible statuses: - SUBMISSION_FAILED - RETRY_PENDING - ON_HOLD

Do not roll back the committed local order.

================================================================================
3. WEBHOOK AND STATUS UPDATE FLOW
================================================================================

STEP 25: RECEIVE WEBHOOK Endpoint: POST /api/webhooks/:provider

Possible events: - case.created - verification.started -
verification.updated - verification.completed - report.ready

STEP 26: VERIFY WEBHOOK AUTHENTICITY Verify: - Signature - Provider
secret/token - Timestamp where supported - Replay protection - Provider
identity

STEP 27: STORE WEBHOOK EVENT Table: webhook_events - id UUID PK -
provider_id UUID FK - external_event_id VARCHAR NULL - event_type -
payload JSONB - processed BOOLEAN - processing_attempts INT -
received_at - processed_at NULL - error_message NULL

Recommended: UNIQUE(provider_id, external_event_id)

STEP 28: UPDATE ORDER VERIFICATION Match using: -
provider_reference_id - provider_case_id - external event IDs

Update: - status - started_at - completed_at - findings - remarks

STEP 29: STORE VERIFICATION RESULT Table: verification_results - id UUID
PK - order_verification_id UUID FK - provider_response JSONB - result
VARCHAR - report_url TEXT NULL - result_received_at - raw_response JSONB
NULL - created_at - updated_at

STEP 30: UPDATE OVERALL ORDER STATUS Example: - All waiting -> PENDING -
At least one active -> IN_PROGRESS - Some complete, some active ->
PARTIALLY_COMPLETED - All required complete -> COMPLETED - Blocking
issue -> ON_HOLD

Every change creates order_status_history.

================================================================================
4. REPORT, BILLING, AND NOTIFICATION FLOW
================================================================================

STEP 31: STORE FINAL REPORT Table: report_files - id UUID PK - order_id
UUID FK - order_verification_id UUID FK NULL - file_name - storage_url -
file_type - generated_at - uploaded_at

Use controlled object storage. Avoid permanent public URLs.

STEP 32: CREATE INVOICE IF REQUIRED Table: invoices - id UUID PK -
order_id UUID FK - company_id UUID FK - invoice_number VARCHAR UNIQUE -
amount NUMERIC(12,2) - tax NUMERIC(12,2) - discount NUMERIC(12,2) -
total NUMERIC(12,2) - currency - status - issue_date - due_date -
paid_at NULL - created_at - updated_at

Invoice from historical order price snapshots, not current prices.

STEP 33: NOTIFY CLIENT Use: - notifications - email_logs

Examples: - Order submitted - Verification started - Additional document
required - Verification completed - Final report ready - Invoice
generated

================================================================================
5. HIGH-LEVEL RELATIONSHIPS
================================================================================

COMPANIES -> BRANCHES -> USERS -> APPLICANTS -> APPLICANT_ADDRESSES ->
IDENTITY_DOCUMENTS -> ORDERS -> ORDER_STATUS_HISTORY -> CONSENTS ->
ORDER_VERIFICATIONS -> SERVICES -> PROVIDERS -> VERIFICATION_RESULTS ->
BGV_API_REQUESTS -> REPORT_FILES -> INVOICES

PROVIDERS -> WEBHOOK_EVENTS

================================================================================
6. RECOMMENDED ORDER STATUS FLOW
================================================================================

Normal: DRAFT -> PENDING_CONSENT -> READY_FOR_SUBMISSION -> SUBMITTED ->
IN_PROGRESS -> PARTIALLY_COMPLETED -> COMPLETED

Exceptions: - ON_HOLD - FAILED - CANCELLED - DISPUTED

Not every order must pass through every state.

================================================================================
7. RECOMMENDED VERIFICATION STATUS FLOW
================================================================================

PENDING -> WAITING_FOR_CONSENT -> READY_FOR_SUBMISSION -> SUBMITTED ->
IN_PROGRESS -> COMPLETED

Exceptions: - SUBMISSION_FAILED - RETRY_PENDING - ON_HOLD - CANCELLED -
DISPUTED

================================================================================
8. TRANSACTION BOUNDARY
================================================================================

INSIDE MAIN TRANSACTION: BEGIN - Find/create applicant - Store applicant
address/contact if applicable - Create order - Create order
verifications - Store historical price snapshots - Link/store consent -
Create order status history - Create activity log COMMIT

OUTSIDE MAIN TRANSACTION: - Queue provider submission - Call third-party
API - Send emails - Send notifications - Generate reports - Process
webhooks

================================================================================
9. IMPORTANT SECURITY AND DATA RULES
================================================================================

1.  Never trust company_id from frontend.
2.  Derive company from authenticated user.
3.  Verify branch access.
4.  Never trust frontend prices.
5.  Load authoritative pricing from PostgreSQL.
6.  Snapshot charged prices.
7.  Encrypt sensitive identity data.
8.  Do not call Aadhaar an SSN.
9.  Do not log raw identity numbers, passwords, tokens, or API keys.
10. Use parameterized SQL or safe ORM/query builder.
11. Use foreign keys.
12. Use unique constraints.
13. Index foreign keys and common filters.
14. Verify webhook signatures.
15. Make webhook processing idempotent.
16. Make order creation idempotent.
17. Use secure object storage for reports/documents.
18. Apply tenant filters to every client-owned query.
19. Define retention/deletion rules for sensitive BGV data.
20. Prefer a secrets manager for provider credentials.

================================================================================
10. RECOMMENDED INDEXES
================================================================================

orders: - INDEX(company_id, created_at) - INDEX(company_id, status) -
INDEX(branch_id, created_at) - INDEX(applicant_id) - INDEX(ordered_by) -
UNIQUE(order_number) - UNIQUE(idempotency_key)

order_verifications: - INDEX(order_id) - INDEX(service_id) -
INDEX(provider_id) - INDEX(status) - INDEX(provider_case_id)

applicants: - INDEX(company_id, email) - INDEX(company_id, phone)

bgv_api_requests: - INDEX(order_id) - INDEX(order_verification_id) -
INDEX(provider_id, status) - INDEX(provider_reference_id)

webhook_events: - INDEX(provider_id, received_at) - INDEX(processed,
received_at)

order_status_history: - INDEX(order_id, changed_at)

================================================================================
11. FINAL END-TO-END PROCESS
================================================================================

1.  Client clicks Place Order
2.  POST /api/orders with token and Idempotency-Key
3.  Authenticate client user
4.  Authorize order:create
5.  Derive company_id from authenticated user
6.  Validate request
7.  Validate branch access
8.  Validate package and selected services
9.  Validate consent requirements
10. Load authoritative prices
11. Calculate subtotal, discount, tax, total
12. Check idempotency key
13. BEGIN
14. Find/create applicant within company
15. Store/update applicant details
16. Store address/contact where applicable
17. Create order
18. Generate concurrency-safe order number
19. Create one order_verification per selected service
20. Snapshot all charged prices
21. Link/store consent
22. Create initial order_status_history
23. Create activity_log
24. COMMIT
25. Reliably queue provider submission
26. Create bgv_api_requests record
27. Worker calls third-party BGV provider
28. Save provider reference/case IDs
29. Update verification/order status
30. Receive provider webhook
31. Verify webhook authenticity
32. Store webhook event idempotently
33. Update order_verifications
34. Store verification_results
35. Recalculate overall order status
36. Store final report metadata
37. Create invoice if required
38. Notify client

================================================================================
12. FINAL ASSESSMENT
================================================================================

The original process had the correct foundation: - POST order request -
BEGIN transaction - Insert applicant - Insert order - Insert selected
verification services - COMMIT

The updated process keeps that foundation and adds: - Multi-tenant
safety - Branch ownership - ordered_by tracking - Applicant duplicate
handling - Historical price snapshots - Consent management -
Idempotency - Safe order numbering - Status history - Activity logging -
Third-party provider API integration - Retry tracking - Webhook
processing - Verification results - Reports - Billing - Notifications -
Sensitive data protection

This is the recommended updated implementation flow for the EvalRight
BGV platform.
